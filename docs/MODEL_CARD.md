# NodeSense Model Card

Applies to the transformer classifier committed at `backend/artifacts/model.onnx`
and served by `backend/app.py`. Numbers below are regenerated by
`backend/evaluate.py`, `backend/zero_day_eval.py`, `backend/benchmark.py`,
and `backend/global_importance.py` — re-run them after retraining and update
this file's numbers to match.

## Intended use

- **Educational / research demonstration** of explainable network intrusion
  detection: a sequence transformer classifying network flow sessions into
  six classes (Benign, DDoS, Port Scan, Brute Force, Botnet, Infiltration),
  paired with per-alert SHAP explanations.
- A worked example of the full ML systems loop — synthetic data generation,
  multi-model benchmarking, ONNX export, explainability, and a served
  dashboard — for a graduate independent study project.
- A **reference architecture** a security team could adapt: swap in real
  traffic and a production-scale model behind the same serving/explanation
  interface.

## Out of scope

- **Not production-ready intrusion detection.** The shipped model is trained
  on synthetic data (see below) and has not been validated against live
  network traffic, adversarial evasion, or the CICIDS-2018 dataset's known
  labeling issues.
- **Not a replacement for signature-based tools.** NodeSense is designed to
  complement, not replace, tools like Snort — it catches novel patterns,
  not known-bad byte sequences.
- **Not hardened against adversarial input.** No adversarial robustness
  testing has been done; an attacker who can shape their flow statistics to
  resemble benign traffic (mimicry) is not accounted for.
- **Not calibrated for a specific network's base rate.** The confidence
  threshold and false-positive behavior below reflect the evaluation set's
  class balance (~55% benign), not any particular deployment's traffic mix.

## Training data

**The model committed to this repository is trained on synthetic data**,
generated by `backend/data.py`. This is a clearly documented and important
caveat: the synthetic generator draws each class from hand-tuned
distributions chosen to mirror published flow-level attack signatures
(e.g., port scans as near-instant single-SYN flows, botnet beaconing as
long idle periods with periodic check-ins), but it is not real traffic, and
its classes are more cleanly separable than real network data — see
"Known limitations" below.

The same pipeline (`backend/train.py`) also accepts the real
[CICIDS-2018 dataset](https://www.unb.ca/cic/datasets/ids-2018.html) via
`--data "../data/*.csv"`; `data.py` maps CICIDS-2018's column names onto the
same 20-feature vector so a model trained on either source serves
identically. **A model trained on real CICIDS-2018 has not yet been
evaluated or shipped** — this is the most important piece of unfinished
work for turning this from a systems demo into a research result (see
Priority 5.2 in the improvements log).

## Reported metrics

From `backend/artifacts/eval/metrics.json` (regenerate with
`python evaluate.py`), evaluated on a held-out 20% split of the synthetic
dataset (800 of 4,000 sessions), the same split the shipped model was
never trained on:

| Metric | Value |
|---|---|
| Accuracy | 1.000 |
| Macro F1 | 1.000 |
| Weighted F1 | 1.000 |
| Benign false positive rate | 0.000 |

Per-class precision/recall/F1 are all 1.000 across Benign, DDoS, Port Scan,
Brute Force, Botnet, and Infiltration (see `metrics.json` and
`confusion_matrix.png` for the full breakdown).

**These numbers are expected to look "too good," and that is itself the
finding to report, not hide:** the synthetic generator's classes are
statistically well-separated by construction, so a saturated score here
demonstrates the pipeline works end-to-end, not that the model has solved
real-world intrusion detection. The number that matters for the paper is
the same evaluation re-run against real CICIDS-2018 data.

### Confidence calibration

From `backend/artifacts/eval/calibration.json`: raw softmax confidence has
an Expected Calibration Error (ECE) of 0.0065 on the held-out set (already
low, another symptom of how separable the synthetic classes are — real
data will show a larger gap). Temperature scaling was fit as a
demonstration (T=0.5, ECE -> 0.0000) but **is not applied in serving** —
`/predict` returns raw softmax confidence. Fitting and evaluating
calibration on the same split (rather than a separate calibration set) is
a known limitation of this analysis; treat it as a worked example of the
technique, not a validated calibration.

### Zero-day generalization (leave-one-attack-out)

From `backend/artifacts/eval/zero_day.json`: for each attack class, a model
was retrained with every session of that class removed, then scored on
whether it still flagged that class's held-out test sessions as *some*
anomaly (a model that never saw a class during training cannot be expected
to name it correctly — only to notice the traffic looks wrong). This is
the closest approximation to "how does NodeSense do against a genuinely
novel attack" that a synthetic, offline evaluation can offer.

| Held-out class | Zero-day anomaly recall | In-distribution accuracy (same fold) |
|---|---|---|
| DDoS | 1.000 | 1.000 |
| Port Scan | 1.000 | 1.000 |
| Brute Force | 0.974 | 1.000 |
| Botnet | 0.986 | 1.000 |
| Infiltration | **0.000** | 1.000 |

**This is the most substantive research finding in the project, and it is
a negative result worth reporting prominently rather than omitting:** a
model that has never seen DDoS, Port Scan, Brute Force, or Botnet traffic
still flags nearly all of it as anomalous when confronted with it for the
first time — genuine zero-day-style generalization. Infiltration is the
one class where this completely fails (0/72 held-out sessions flagged).

The likely explanation is not a bug but a property of the attack itself:
`data.py`'s Infiltration generator models data exfiltration as long flows
dominated by large server-to-attacker transfers — deliberately similar to
legitimate large downloads, which is exactly how real exfiltration attacks
evade detection in practice (see "Ethical considerations" — this is a
known, intentional evasion strategy, not an artifact of the synthetic
data). A model that has never been shown a labeled infiltration example
has nothing in its representation to distinguish "large transfer, attack"
from "large transfer, benign." In-distribution accuracy staying at 1.000
in the same fold confirms the model isn't degraded generally — it
specifically cannot generalize to the one class whose flow statistics
overlap benign traffic by design.

This result is exactly the kind of finding a real deployment needs to know
going in: **NodeSense generalizes well to novel attacks with distinctive
flow signatures, but should not be assumed to catch novel exfiltration-style
attacks without exfiltration-labeled training examples.**

## Known limitations

- **Synthetic data caveat** (repeated because it is the single most
  important thing to disclose): every metric above describes performance
  on a generator whose classes are, by construction, more separable than
  real traffic. Do not cite these numbers as evidence of real-world
  detection accuracy.
- **CICIDS-2018 labeling issues.** If/when this model is retrained on real
  CICIDS-2018 data, note that the dataset has documented labeling and
  generation problems — see Engelen, Rimmer & Joosen, "Troubleshooting an
  Intrusion Detection Dataset: the CICIDS2017 Case Study" (2021), which
  identifies mislabeled flows and artifacts from the dataset's traffic
  generation process in the closely related CICIDS-2017/2018 family.
  Numbers from the raw dataset should be reported alongside this caveat,
  and a corrected/relabeled release should be preferred if available.
- **Small model, small synthetic dataset.** ~150k parameters trained on
  4,000 sessions (64,000 flows). This is intentionally compact for fast
  CPU inference and SHAP explanation; it has not been scaled up or tuned
  against a large real dataset.
- **Single-instance, single-process assumptions.** The rate limiter and
  WebSocket connection cap in `app.py` use in-process memory; a
  multi-worker or multi-instance deployment needs a shared backend
  (e.g., Redis) for these to be meaningful at scale.

## Ethical considerations

- **Alert fatigue and analyst trust.** A false positive rate that looks
  negligible in a clean synthetic evaluation can still translate into a
  noisy, trust-eroding alert stream on real, messier traffic. The SHAP
  explanation layer is meant to help analysts triage and calibrate trust,
  but it does not substitute for validating false-positive rates on
  traffic representative of the deployment network before relying on this
  system operationally.
- **Human-in-the-loop requirement.** NodeSense is designed to inform an
  analyst's decision, not to autonomously block traffic. No automated
  response/blocking logic exists in this codebase, and none is
  recommended without separate, deployment-specific validation.
- **Dual-use nature of the synthetic attack generator.** `backend/data.py`
  encodes descriptions of how several attack classes look at the network
  flow level. This is standard, published knowledge (the same
  characteristics documented in CICIDS-2018 and general IDS literature)
  used here purely to generate labeled training data, not to construct or
  automate an attack — no packet-crafting or exploit code exists in this
  project.
- **No personal or sensitive data.** All traffic in this project — both the
  synthetic generator and the CICIDS-2018 integration path — is network
  flow metadata (packet counts, timings, byte rates), not payload content,
  and the demo mode's live alert stream is entirely synthetic.
